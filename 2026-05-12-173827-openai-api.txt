● 这个报错的含义是：还没请求你的 OpenAI 兼容接口，后端本地用 FFmpeg 
  抽帧就已经一张都没抽出来。

  代码位置：

  - commentary.py:2868 开始抽取 OpenAI 兼容模式用的密集时间线帧
  - commentary.py:1276 _extract_openai_analysis_frames(...)
  - commentary.py:1414 如果 frame_infos 为空，就抛出：
  OpenAI-compatible analysis mode could not extract any video frames

  常见原因：

  1. FFmpeg 不可用或容器里缺 FFmpeg
    - 这个模式必须本地执行 ffmpeg -ss ... -i video -frames:v 1 ...jpg
    - 如果 Docker/后端环境里 FFmpeg 缺失或不可执行，就会全部失败。
  2. 输入视频路径或视频文件不可读
    - 上传/下载的视频可能损坏、为空、格式不被当前 FFmpeg 解码。
    - 如果是 YouTube 链接，也可能下载到的是异常文件。
  3. 视频 duration 被识别为 0
    - _get_video_info() 用 OpenCV 读时长；如果 OpenCV 读不到
  fps/frame_count，duration 会是 0，抽帧直接返回空。
  4. FFmpeg 抽帧滤镜失败
    - 当前命令含有：
  -vf scale=-2:360
    - 如果某些视频解码失败、像素格式异常、路径问题，所有帧都会失败。
  5. 后端吞掉了具体 FFmpeg 错误
    - commentary.py:1327 这里 except Exception: 
  continue，导致真实原因没显示出来，只显示最终“没有抽到帧”。

  你可以先在后端运行环境里检查：

  ffmpeg -version

  再对出问题的视频手动试一下：

  ffmpeg -y -ss 1.000 -i "你的视频文件路径" -frames:v 1 -vf scale=-2:360 -q:v 4
  /tmp/test-frame.jpg

  如果这个命令失败，stderr 就是真正原因。

  最可能的快速修复方向是：把 commentary.py:1327
  的吞错改成记录日志，例如抽帧失败时输出 FFmpeg stderr，这样前端能看到到底是
  ffmpeg not found、Invalid data found、路径问题，还是解码问题。

● 是的，现在是串行分析。

  流程大概是：

  抽完全部帧
  ↓
  batch 1 请求 OpenAI 兼容接口，等返回
  ↓
  batch 2 请求，等返回
  ↓
  batch 3 请求，等返回
  ...
  ↓
  batch 41 请求，等返回
  ↓
  汇总所有 batch 的视觉观察
  ↓
  再请求一次模型写完整解说脚本

  也就是说：

  - 不是并发 41 个请求
  - 是 前一批返回后才开始下一批
  - 所以你看到 batch 29/41...，表示前 28 批已经返回并解析完了，第 29
  批正在请求/等待返回

  当前代码在 commentary.py 里这里串行执行：

  for index, batch in enumerate(batches, start=1):
      ...
      text = _call_openai_compatible_chat(...)

  为什么一开始做成串行：

  - 避免把本地代理 / OpenRouter / 硅基流动 / 火山 / 通义兼容接口打爆
  - 避免并发上传大量 base64 图片导致内存暴涨
  - 避免触发 rate limit
  - 保证日志顺序和错误定位简单

  但缺点就是你现在看到的：完整视频 + 1312 张图 + 41 批，会非常慢。

  可以优化成“有限并发”，比如同时跑 2～4 个 batch：

  batch 1,2,3,4 同时请求
  等谁先返回就记录谁
  继续补 batch 5...

  这样总耗时会明显下降，但要加：

  - 并发数配置，比如 OPENSHORTS_OPENAI_VISUAL_CONCURRENCY=3
  - 每批独立错误处理
  - 结果按 batch_index 排序合并
  - 避免接口限流时全部失败

  我建议先加一个保守并发：默认 1，用户可配置 2～4。这样 Docker
  和默认行为不变，你本地可以开到 3。
